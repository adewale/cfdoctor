### Severity: medium — Unchanged scheduled snapshots repeatedly consume the write meter

- Category: cost footgun
- Evidence: `index.js:2` fixes the input at 1,000 unchanged rows; `index.js:9–14` deletes and reinserts every row without a content/version check. `wrangler.jsonc:6` schedules this every five minutes. `evidence.txt:6–14` explicitly supplies identical prior data and completed-run metadata: 1,000 deleted rows plus 1,000 inserted rows, with zero sampled reads.
- Why it matters: D1 counts both `DELETE` and `INSERT` toward rows written. Database size, quiet HTTP traffic, and owner count do not prevent scheduled operations from accumulating usage. The hypothetical 576,000 daily writes exceed the documented Free-plan allowance of 100,000 writes/day; on that plan queries would stop at the applicable account limit, so a full successful day cannot be assumed. Paid allowances and overages use a different monthly window. This evidence does not establish any charge: the actual plan, matching account totals, allowance consumption, and subscription window are absent.
- Fix: For this fixed in-memory snapshot, import once and trigger another import only when its source version changes; remove the unconditional periodic rebuild. If periodic discovery must remain, compare a stable digest against the last successfully applied version before any destructive SQL and return on an unchanged version. Persist that marker durably, account for any lookup/read overhead, and update it only with a successful import. On changed imports, apply only actual additions, changes, and removals. If retaining a full replacement for simplicity, use an atomic D1 `batch()` for the replacement and marker so a failure rolls back the change; batching alone does not eliminate the 2,000-row rewrite.
- Cost / trade-off: An unchanged invocation should perform zero snapshot writes. An explicit change trigger can eliminate the recurring D1 queries entirely; a database-backed version check introduces measured reads. Change detection adds state and synchronization work, and changed-data imports still consume reads/writes. Avoid unconditional upserts as a presumed saving; prove the no-change path skips writes. No new product or index is needed to address this mechanism.
