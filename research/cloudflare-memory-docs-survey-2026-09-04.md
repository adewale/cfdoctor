# Cloudflare memory-load documentation survey — 2026-09-04

## Why this exists

Polylane's post "How We Fixed Our Cloudflare Durable Objects Memory Exceeded Errors" (Aleksandr Diamond and Boris Tane, 2026-08-26, https://polylane.com/blog/how-we-fixed-our-cloudflare-durable-objects-memory-exceeded-errors/) describes ~300 Durable Object resets a day caused by module-scope baseline memory (zod schemas plus un-tree-shaken barrels) in an isolate that has a fixed 128 MB ceiling. The question for cfdoctor was how much of that is Cloudflare-specific and whether it belongs in the skill at all.

This note answers that by surveying what Cloudflare's own documentation says about memory across the developer platform, so the follow-up PR can be organised around **memory load as a failure class** rather than around one war story. War stories remain scenario prompts; the statements below are the doc-backed product facts the skill may cite.

## Scope and method

- Downloaded the per-product `llms-full.txt` documentation exports on 2026-09-04 for: workers, durable-objects, workflows, pages, containers, browser-run, dynamic-workers, agents, queues, kv, r2, d1, hyperdrive, workers-ai, vectorize, sandbox, cloudflare-for-platforms, pipelines, rules (Snippets), email-service, images, stream, ai-gateway.
- Grepped each export for `memory`, `heap`, `OOM` / `out of memory`, `evict`, `exceeded`, `startup time`, `Worker size`, `memoryUsage`; de-duplicated repeated note blocks; then read the matching pages in full for the Workers limits, errors, metrics, streams, node:fs, RPC lifecycle, and Python pages; the Durable Objects metrics, in-memory state, lifecycle, storage API, pricing, troubleshooting, and limits pages; the D1 debug page; the Containers limits and FAQ pages; the Agents SDK recovery and sessions pages.
- Live-verified with a second fetch: Workers limits (memory, startup, size), Durable Objects metrics, Durable Objects limits (no memory section), Wrangler bundling page, and esbuild's tree-shaking documentation.
- Excluded as noise: the Agent Memory product, "memory" in Vectorize and AI Gateway marketing copy, and the 8 GB memory of Workers Builds (build-time, not runtime).
- Zero hits for runtime memory in: queues, hyperdrive, cloudflare-for-platforms. Pipelines and Stream hits were about Parquet row groups and encoder buffers, not the Workers runtime.

Everything below is a paraphrase or short quote of current doc text with its page URL. Re-verify with `scripts/check_links.py` before relying on wording; none of it is pricing authority.

## 1. Platform facts, by surface

### 1.1 The isolate memory limit (Workers, Pages Functions, Email Workers, D1 operations, Agents)

- **Limit.** "Each isolate can consume up to 128 MB of memory, including the JavaScript heap and WebAssembly allocations. This limit is per-isolate, not per-invocation. A single isolate can handle many concurrent requests." Same value on Free and Paid. https://developers.cloudflare.com/workers/platform/limits/#memory
- **Behaviour on exceed (Workers).** "When an isolate exceeds 128 MB, the Workers runtime lets in-flight requests complete and creates a new isolate for subsequent requests. During extremely high load, the runtime may cancel some incoming requests to maintain stability." Same page.
- **Error surfaces.** Client receives Error 1102 `Worker exceeded resource limits`; the dashboard shows `Exceeded Memory` under Metrics > Errors > Invocation Statuses; analytics and Logpush record the invocation outcome `exceededMemory`; the runtime error `Memory limit would be exceeded before EOF` appears when buffering a body that would cross the limit. Same page. The Tail handler lists `exceededMemory` as an outcome and notes a `waitUntil()` task can exceed CPU or memory after a `200` has already been sent. https://developers.cloudflare.com/workers/runtime-apis/handlers/tail/ Trace spans expose the same outcome as `cloudflare.outcome`. https://developers.cloudflare.com/workers/observability/traces/spans-and-attributes/ `ctx.passThroughOnException()` "does not mitigate failures such as exceeding CPU or memory limits." https://developers.cloudflare.com/workers/runtime-apis/context/
- **Documented remedies.** Stream request and response bodies; keep large data in KV, R2, or D1 instead of Worker memory; profile locally with DevTools heap snapshots. https://developers.cloudflare.com/workers/platform/limits/#memory
- **Other surfaces that inherit it.** Pages Functions: exceeding memory can still throw despite the try/catch fallback around `passThroughOnException()` (https://developers.cloudflare.com/pages/platform/known-issues/); `Exceeded resources` status maps to 1102/1027 (https://developers.cloudflare.com/pages/functions/metrics/). Email Workers "count toward the standard Workers CPU and memory limits" and complex handlers can fail on the Free plan (https://developers.cloudflare.com/email-service/platform/limits/). D1: "Operations on a D1 database, including query execution and result serialization, run within the Workers platform CPU and memory limits" (https://developers.cloudflare.com/d1/platform/limits/). Agents: "Many limits are inherited from those applied to Workers scripts and/or Durable Objects" (https://developers.cloudflare.com/agents/platform/limits/).

### 1.2 Startup-time validation: baseline memory and baseline CPU are deploy-time failures

- **Startup memory.** Under the 10021 validation errors: "Script startup exceeded memory limit — This means that you are doing work in the top-level scope of your Worker that allocates more than the memory limit (128 MB) of memory." https://developers.cloudflare.com/workers/observability/errors/
- **Startup CPU.** "A Worker must parse and execute its global scope (top-level code outside of handlers) within 1 second. Larger bundles and expensive initialization code in global scope increase startup time." Rejected deploys return `Script startup exceeded CPU time limit` (10021); Wrangler auto-generates a CPU profile; `wrangler check startup` and the `startup_time_ms` field in deploy output measure it. The docs name the common cause: "generating or consuming a large schema at the top level is a common cause of exceeding this limit." https://developers.cloudflare.com/workers/platform/limits/#worker-startup-time and https://developers.cloudflare.com/workers/wrangler/commands/workers/
- **Worker size.** 3 MB (Free) / 10 MB (Paid) after gzip, 64 MB before; "Larger Worker bundles can impact startup time"; measure with `wrangler deploy --outdir bundled/ --dry-run`; reduce by dropping dependencies, moving assets to KV/R2/D1/Static Assets, or splitting Workers via Service bindings. https://developers.cloudflare.com/workers/platform/limits/#worker-size Wasm Workers "are typically larger" and "may take your Worker longer to start" (https://developers.cloudflare.com/workers/runtime-apis/webassembly/).
- **Dynamic Workers** bill "Startup time: The compute required to initialize the isolate and parse your code" as a separate meter (https://developers.cloudflare.com/dynamic-workers/pricing/), so baseline weight is also a per-load cost there.

Together these mean the Polylane failure has two documented deploy-time cousins on plain Workers: the same module-scope weight that trips DO isolate memory at runtime trips `Script startup exceeded memory limit` or `Script startup exceeded CPU time limit` at deploy time, and the docs already single out top-level schema work as the usual culprit.

### 1.3 Durable Objects: shared isolate, resets, eviction, and memory as a billing unit

- **Per-isolate measurement, shared across objects.** "Memory is measured per isolate, not per Durable Object. A single isolate can host multiple Durable Objects of the same class, along with the surrounding Worker code, and they all share that isolate's memory. The chart always reports the memory of the whole isolate, not an individual Durable Object." Filtering by ID or name still returns whole-isolate samples. Data comes from the `durableObjectsPeriodicGroups` GraphQL dataset, `memoryUsageBytes`, with `quantiles.memoryUsageBytesP50` through `memoryUsageBytesP999`. Upward trend is called out as a leak signal, with local DevTools as the remedy. https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/#memory-usage
- **Global memory is shared between instances.** "A given instance of a Durable Object may share global memory with other instances defined in the same Worker code," so module-level variables are shared and the docs say to avoid them. The same page has an "Observe in-memory state size" section pointing at the memory chart. https://developers.cloudflare.com/durable-objects/reference/in-memory-state/
- **Reset semantics.** Historical changelog: "When a Durable Object's isolate exceeds its memory limit, an exception with an explanatory message will now be thrown to the caller, instead of 'internal error'"; and "When a Durable Object's code is updated, or when its isolate is reset due to exceeding the memory limit, all stubs pointing to the object will become invalidated and have to be recreated." https://developers.cloudflare.com/workers/platform/changelog/historical-changelog/ Troubleshooting: "Reset in error messages refers to in-memory state. Any durable state that has already been successfully persisted via `state.storage` is not affected." https://developers.cloudflare.com/durable-objects/observability/troubleshooting/
- **The Agents SDK treats memory-limit resets as expected.** Think durable recovery has `maxOomRetries` (default 3): "Retry budget for Durable Object memory-limit resets. Set 0 to stop after the first memory-limit reset," and `out_of_memory` is one of the recovery-exhausted reasons. https://developers.cloudflare.com/agents/harnesses/think/recovery/ and https://developers.cloudflare.com/agents/communication-channels/chat/chat-agents/ The Sessions page explains why the SDK does not use tiktoken: "Tiktoken would add 80–120 MB heap overhead, which exceeds Cloudflare Workers' 128 MB limit." https://developers.cloudflare.com/agents/runtime/lifecycle/sessions/
- **Lifecycle.** Hibernation after 10 seconds idle when eligible; eviction after 70–140 seconds idle when not; an outbound `connect()` or WebSocket pins the object in memory for up to 15 minutes; in-memory state is discarded on hibernation, eviction, crash, or code update. https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/ The Agents docs list eviction causes as inactivity, "code updates / runtime restarts — non-deterministic, 1–2x per day," and alarm timeouts, and warn that "In-memory variables, timers, open fetches, and local closures do not survive eviction." https://developers.cloudflare.com/agents/runtime/execution/durable-execution/
- **WebSockets and memory.** Non-hibernating connections "pin your Durable Object to memory" and incur duration charges; the Hibernation API lets the object be "removed from memory" while sockets stay open; the 32,768-connection cap comes with "the CPU and memory usage of a given workload may further limit the practical number." https://developers.cloudflare.com/durable-objects/best-practices/websockets/ and https://developers.cloudflare.com/durable-objects/api/state/
- **Storage API memory hazards.** `list()` without options: "all the data will be loaded into the Durable Object's memory, potentially hitting its limit." `put()` writes to an in-memory write buffer that "could theoretically grow large enough to cause" problems if many puts are issued without awaiting I/O; `noCache` and `allowUnconfirmed` are hints for memory and durability behaviour. https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/
- **Memory is the DO duration billing unit.** "Duration billing charges for the 128 MB of memory your Durable Object is allocated, regardless of actual usage. If your account creates many instances of a single Durable Object class, Durable Objects may run in the same isolate on the same physical machine and share the 128 MB of memory. These Durable Objects are still billed as if they are allocated a full 128 MB of memory." https://developers.cloudflare.com/durable-objects/platform/pricing/
- **Doc gap at Cloudflare.** The Durable Objects limits page has no memory row (https://developers.cloudflare.com/durable-objects/platform/limits/); the concepts page says only "similar memory and CPU limits" to Workers (https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/); the Wrangler bundling page documents `--dry-run --outdir` but nothing about tree shaking, `sideEffects`, or memory (https://developers.cloudflare.com/workers/wrangler/bundling/). The number and the per-isolate semantics live only on the Workers limits page and the DO observability page.

### 1.4 Request-path buffering

- "Use the Streams API to avoid buffering large requests or responses in memory. This enables you to parse extremely large request or response bodies within a Worker's 128 MB memory limit." https://developers.cloudflare.com/workers/runtime-apis/streams/
- Best practices: "Workers have a 128 MB memory limit, so buffering an entire body with `await response.text()` or `await request.arrayBuffer()` will crash your Worker on large payloads." Concatenate upstream responses by piping into one writable stream rather than buffering. https://developers.cloudflare.com/workers/best-practices/workers-best-practices/
- `request.clone()` for repeated body reads: "loading particularly large files into a Worker's memory multiple times may reach this limit" (repeated in the R2, Images, and form-handling tutorials, for example https://developers.cloudflare.com/r2/api/workers/workers-api-usage/). Historical changelog: an unread cloned body "forces the runtime to buffer the entire message body in memory." https://developers.cloudflare.com/workers/platform/changelog/historical-changelog/ `response.body.cancel()` "is still good practice to free memory" when a fetched body is unused. https://developers.cloudflare.com/workers/platform/limits/#memory
- `node:fs` temporary files are in-memory: "the total size of all temporary files and directories created count towards your Worker's memory limit. If you exceed this limit, the Worker instance will be terminated and restarted." https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/
- RPC: "When you call another Worker over RPC using a Service binding, you are using memory in the Worker you are calling"; the RPC page shows buffering into memory as a pattern that "puts a lot of memory pressure on the isolate" and recommends chunking. https://developers.cloudflare.com/workers/runtime-apis/rpc/lifecycle/ and https://developers.cloudflare.com/workers/runtime-apis/rpc/
- KV: a single large value's "size of the resultant value can push your worker out of its memory limits." https://developers.cloudflare.com/kv/api/read-key-value-pairs/ R2 `list()` "may return less [than 1000] in order to minimize memory pressure within the Worker." https://developers.cloudflare.com/r2/api/workers/workers-api-reference/ Sandbox SDK: `output()` "buffers both streams in memory. For large output, drain `stdout` and `stderr` concurrently instead." https://developers.cloudflare.com/sandbox/guides/execute-commands/

### 1.5 Python and Wasm

- Python Workers execute the entrypoint and all top-level imports at deploy time and snapshot the Wasm linear memory, "effectively, we perform the expensive initialization work at deploy time, rather than at runtime." https://developers.cloudflare.com/workers/languages/python/how-python-workers-work/ The Python in-memory filesystem is "lost when the Worker isolate is destroyed" and not shared between isolates. https://developers.cloudflare.com/workers/languages/python/stdlib/
- Wasm allocations count inside the 128 MB (limits page); historically a module declaring growth beyond 128 MB failed at load, now "the actual memory usage of the module is monitored and an error is thrown if it exceeds 128MB used." https://developers.cloudflare.com/workers/platform/changelog/historical-changelog/

### 1.6 Data-plane memory failures outside your code

- D1: "D1 DB's isolate exceeded its memory limit and was reset. — A query loaded too much into memory, causing the D1 database to crash. App action: Optimize the queries (so that each query takes less time), send fewer requests by spreading the load over time, or shard the queries." https://developers.cloudflare.com/d1/observability/debug-d1/
- Vectorize: too many unique metadata values in a filtered range forces large index reads; "This would lead to memory issues, so Vectorize will degrade performance and the accuracy of the query in order to finish the request." https://developers.cloudflare.com/vectorize/best-practices/insert-vectors/

### 1.7 Sized runtimes: Containers, Browser Run, Snippets, Dynamic Workers, Workflows

- Containers: memory comes from instance types (six named types or a custom type; `lite` is the default and the Wrangler `memory_mib` default is 256); maximum 12 GiB per instance, minimum 3 GiB memory per vCPU, maximum 2 GB disk per 1 GiB memory, 6 TiB concurrent memory per account. "If you run out of memory, your instance will throw an Out of Memory (OOM) error and will be restarted. Containers do not use swap memory." Memory and disk are billed on provisioned resources, CPU on active usage. https://developers.cloudflare.com/containers/platform/limits/ , https://developers.cloudflare.com/containers/faq/ , https://developers.cloudflare.com/containers/platform/pricing/ , https://developers.cloudflare.com/workers/wrangler/configuration/
- Browser Run: "Chromium crashed — The Chromium instance inside the session crashed, often because the page consumed too much memory (large DOMs, heavy JavaScript, or many concurrent pages)"; all tabs "share the same browser process and memory"; Kitesurf is documented as using 3–7x less memory than Chromium for screenshot and extraction tasks. https://developers.cloudflare.com/browser-run/reference/browser-close-reasons/ and https://developers.cloudflare.com/browser-run/faq/
- Snippets: maximum memory 2 MB; "Error 1204: Snippets exceeded memory limit"; the documented escalation path is "consider using Cloudflare Workers." https://developers.cloudflare.com/rules/snippets/ and https://developers.cloudflare.com/rules/snippets/errors/
- Dynamic Workers: the loader "may be kept warm in memory for a while" with no guarantee; a Durable Object can have "up to ten distinct Dynamic Workers with in-flight requests"; custom resource limits cover CPU time and subrequests, not memory. https://developers.cloudflare.com/dynamic-workers/api-reference/ , https://developers.cloudflare.com/dynamic-workers/platform/limits/ , https://developers.cloudflare.com/dynamic-workers/usage/limits/
- Workflows: "Workflows may hibernate and lose all in-memory state" whenever the engine detects no pending work; script size limits apply per Worker size. https://developers.cloudflare.com/workflows/build/rules-of-workflows/ and https://developers.cloudflare.com/workflows/reference/limits/

## 4. Proposed shape for the PR

Organise the PR as "memory load on Cloudflare" with one scenario per class where a war story exists, and doc-backed guidance where none does.

- **`war-story-scenario-checklist.md`**: add scenario 25 (Polylane, class A) with evidence ID `CFDOC-EVD-POLYLANE-DO-MEMORY`; keep the generic bundling facts clearly labelled as esbuild behaviour confirmed by the authors' fixtures, and the 128 MB / per-isolate / startup-validation facts as Cloudflare doc statements. - **`cost-footguns.md`**: class F, the 128 MB duration denomination and pinned objects.
- **`product-fit-rubric.md`**: there is no larger Durable Object; heavy baseline means restructuring the bundle or moving the heavy part to Containers (which has instance types) or splitting Workers via Service bindings (documented size remedy).
- **`targeted-account-reads.md` / `sharing-cloudflare-state.md`**: ask for DO `memoryUsageBytes` P50/P99 over a week with deployment markers, Workers `exceededMemory` counts, `startup_time_ms` from the last deploy, and Container OOM restart counts.

- **Scanner**: at most two new leads, both low confidence and gated on Cloudflare shape. `DO-ISOLATE-BASELINE-MEMORY`: DO bindings present and either many module-scope schema constructions reachable from the DO code or barrel/side-effect/dynamic-root-import patterns in the workspace; the finding says "measure module-scope heap and startup time" and points at the recipe. `CFDOC-PERF-BODY-BUFFERING`: `request.arrayBuffer()`/`.text()`/`.json()` or `response.text()` on a fetched upstream in a Worker that also proxies or uploads, widening the existing R2 check rather than duplicating it. Do not add standalone checks for `export *`, missing `sideEffects`, or dynamic package-root imports; they fire on every TypeScript monorepo regardless of memory headroom.
- **`docs/recipes.md`**: the local module-scope heap probe (dry-run bundle, instrumented `__esm` helper, Node loader shim, probe entry with placeholder DO class, gotchas), plus `wrangler check startup` and the bundle-size dry-run as the cheaper first pass. Optionally a metafile assertion that fails CI when a schema module survives into a memory-sensitive Worker; keep it in recipes rather than as a repo script.
- **Coverage matrix, README, CHANGELOG, TODO**: as usual for new checks and scenarios.

## 5. Doc gaps worth stating in findings

- The Durable Objects limits page does not mention memory; a reader who only checks that page will not learn about the 128 MB ceiling or that it is shared per isolate.
- The Wrangler bundling page says nothing about tree shaking, `sideEffects`, or memory even though Wrangler owns the esbuild configuration.
- The Workers limits page describes the exceed behaviour for stateless Workers (in-flight requests finish, new isolate); for Durable Objects the observable behaviour is a reset that invalidates stubs and discards in-memory state, documented only in the historical changelog and the troubleshooting page's one-line note.
