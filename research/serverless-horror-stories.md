# Research: Serverless/edge cost blowups and misconfigurations

This is a discovery/research view, not the canonical evidence database. Promote accepted sources and claims into `research/incident-claim-ledger.json`, deduplicated by source cluster and separated into incident observation, operator inference, official guidance, and current product semantics.

Link and claim status last verified: 2026-07-11 (`scripts/check_links.py`; `scripts/check_claim_ledger.py`).

## Summary
Public cost blowups cluster around four patterns: unbounded public traffic, recursive/event-trigger loops, per-operation multipliers such as image transforms/database reads/log ingestion, and “budgets” that alert but do not cap spend. For Cloudflare Doctor, the useful checks are not Cloudflare-only billing checks; they are edge/origin exposure checks: wildcard Workers/Pages routes, self-fetch loops, expensive bindings on public endpoints, cache bypass, image/R2 hotlinking, missing rate limits, and missing usage/anomaly alerts.

## Findings
1. **Serverless turns abuse into spend unless scale is capped.** Vercel added project-level spend management because usage-based products can otherwise continue accruing charges; Netlify publicly addressed surprise bandwidth-billing concerns after a viral DDoS/bandwidth incident; Cloud Run/Azure Functions/AWS Lambda all document scale/concurrency controls rather than assuming the platform will protect cost automatically. [Vercel Spend Management](https://vercel.com/docs/pricing/spend-management), [Netlify billing concerns](https://answers.netlify.com/t/i-am-the-op-of-that-104k-bill-post-and-i-have-some-follow-up-questions/113472) (no archive snapshot found as of 2026-06-09), [Cloud Run max instances](https://cloud.google.com/run/docs/configuring/max-instances), [Azure Functions costs](https://learn.microsoft.com/en-us/azure/azure-functions/functions-consumption-costs), [AWS Lambda recursion](https://docs.aws.amazon.com/lambda/latest/dg/invocation-recursion.html)
2. **Recursive trigger loops are the canonical serverless “denial of wallet.”** AWS documents recursive Lambda detection and throttling; Firebase/Firestore docs warn that writing back to the same watched document can retrigger the function; GCP docs warn retries can repeatedly bill failing functions. [AWS Lambda recursive loop detection](https://docs.aws.amazon.com/lambda/latest/dg/invocation-recursion.html), [Firebase Firestore triggers](https://firebase.google.com/docs/functions/firestore-events), [GCP Cloud Functions retries](https://cloud.google.com/functions/docs/bestpractices/retries)
3. **Seemingly static/cheap platforms have expensive hidden meters.** Netlify bandwidth, Vercel image optimization, Cloudflare KV/D1/R2/Durable Objects operations/duration, Firebase reads/listeners, CloudWatch/Cloud Logging/Application Insights ingestion, and S3 request charges all create non-obvious multipliers. [Vercel Image Optimization pricing](https://vercel.com/docs/image-optimization/limits-and-pricing), [Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [Cloudflare R2 pricing](https://developers.cloudflare.com/r2/pricing/), [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [S3 pricing](https://aws.amazon.com/s3/pricing/)
4. **Budget alerts are often not hard caps.** GCP budgets are alerts unless paired with programmatic controls; AWS Budgets mostly notify unless budget actions are configured; Azure budgets notify, while Azure Functions has a separate Consumption-plan daily quota; Supabase/Railway/Vercel offer stronger spend caps in some plans/products, but teams must explicitly configure them. [GCP budgets](https://cloud.google.com/billing/docs/how-to/budgets), [GCP programmatic notifications](https://cloud.google.com/billing/docs/how-to/budgets-programmatic-notifications), [AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html), [Azure budgets](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets), [Supabase spend cap](https://supabase.com/docs/guides/platform/spend-cap)
5. **Cloudflare Doctor should model third-party-origin risk too.** A Cloudflare zone may front Vercel/Netlify/Railway/Render/Fly/Supabase/Firebase origins; poor cache/rate-limit/origin-lockdown at Cloudflare can pass bot traffic through to those paid origins even if Cloudflare itself has low bandwidth cost.

## Actionable cross-platform checklist

| Check | Why it prevents horror stories | Cloudflare Doctor implementation idea |
|---|---|---|
| **Inventory every public entrypoint and every usage-metered dependency.** | Bills come from public routes invoking paid units: functions, DB reads, storage ops, image transforms, logs, origin egress. | List Cloudflare DNS records, proxied/unproxied origins, Workers routes, Pages projects, R2 public buckets, cache rules, Transform/Image features, Logpush jobs. |
| **Set spend controls before launch.** | Alerts/caps are platform-specific and often off by default. | Warn if no documented billing notification/anomaly process; link runbook for Cloudflare + origin provider budget setup. |
| **Constrain scale/concurrency.** | Default autoscale can convert traffic spikes into spend. | Flag origins known to autoscale serverlessly; recommend provider max instances/reserved concurrency/daily quotas/autoscale max. |
| **Scope functions narrowly.** | Wildcard edge/serverless routes make static assets, crawlers, and health checks billable. | Detect broad Worker routes/Pages Functions and middleware-like route coverage; suggest exclusions for static paths and assets. |
| **Detect self-fetch/redirect/rewrite loops.** | Recursive Workers/Lambda/Functions loops burn invocations and may fail only after platform loop detection. | Check Cloudflare Worker routes + DNS/Rules redirects for same-zone fetch/redirect patterns; manual code review prompt for event triggers. |
| **Protect expensive public APIs.** | Unauthenticated APIs invite bot-driven function/DB/read charges. | For routes with Workers + KV/D1/R2/DO/API origins, require WAF/rate-limit/auth/cache/noindex review. |
| **Lock down image transformation.** | Attackers can create unbounded unique variants via URL/width/quality/remote source. | Flag Cloudflare Image Resizing/Images or proxied Vercel/Netlify image endpoints; require dimension/quality/source allowlists and cache TTL. |
| **Cache static and semi-static responses at the edge.** | Prevents origin egress and serverless invocations at Vercel/Netlify/Railway/Render/Fly/Heroku/GCP/AWS. | Check `Cache-Control`, cookies, query-string cache keys, Cache Rules, bypass rules, large assets, and cache hit ratio if analytics available. |
| **Prevent hotlinking and direct-origin bypass.** | Attackers can skip Cloudflare protections or hammer public storage/app origins. | Flag unproxied DNS, exposed default hostnames (`*.vercel.app`, `*.netlify.app`, `*.railway.app`, `*.onrender.com`, `*.fly.dev`, storage custom domains); recommend origin ACLs, Authenticated Origin Pulls, signed URLs. |
| **Bound retries and poison-message loops.** | Failed events can retry indefinitely or until large queues are exhausted. | Manual provider checklist for SQS/PubSub/Queues/Storage queues: max receives, DLQ, idempotency, no write-back-to-source. |
| **Sample and retain logs deliberately.** | Error storms can make logs the surprise bill. | Flag Cloudflare Logpush/Workers Logs enabled on high-volume routes; recommend sampling, retention, exclusion filters, alerting on log volume. |
| **Prune previews/review apps.** | PR previews can create paid functions, DBs, add-ons, and cacheable public URLs. | Detect preview subdomains under Cloudflare; recommend noindex, TTL cleanup, and no paid add-ons by default. |
| **Run a “denial-of-wallet” game day.** | Many controls only fail under bot-like traffic. | Provide synthetic checklist: hit static asset, function route, image transform, API, storage object; verify rate-limit/cache/auth/alerts fire. |

- Generic “cloud cost optimization” and “serverless cost best practices” listicles — too broad/SEO-heavy; not direct evidence of incidents or platform-specific failure mechanisms.
